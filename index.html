طرق اتصال تطبيقات الويب (Web Application Communication Methods)

لغة التفاهم الرقمي: دورة الطلب والاستجابة، حماية HTTPS بـ TLS، أسلوبا GET و POST، رموز حالة الخادم (200, 404, 500)، وتبادل البيانات المهيكلة بـ API و JSON.

كيف تتحدث المتصفحات مع الخوادم حول العالم عبر أسلاك وأثير الإنترنت؟

تطبيق الويب يعمل كتبادل منظم: العميل يطلب، والخادم يعالج ويستجيب وفق بروتوكولات صارمة!

في الدرس السابق تعلمنا أن تطبيق الويب مبني من واجهة أمامية وخلفية وقاعدة بيانات. في هذا الدرس، نكتشف الشرايين التي تربط هذه الأجزاء: كيف يسافر طلبك عندما تضغط على رابط أو ترسل نموذج تسجيل، وما القواعد (HTTP/HTTPS) التي تحكم المحادثة، وماذا تعني رموز الإجابات التي يعيدها السيرفر؟

الشكل 3.2.1 من كتاب الوزارة ص 58

التواصل بين العميل والخادم (Client-Server Architecture)

دورة الطلب (Request) والاستجابة (Response)

الشكل 3.2.1: يطلب العميل البيانات أو المعالجة، ويعالج الخادم الطلب ويعيد استجابة مطابقة واحدة عبر قواعد بروتوكول HTTP.

1. العميل (Client):

برنامج أو جهاز يرسل طلباً إلى خدمة أخرى (مثل متصفح Google Chrome، أو تطبيق الهاتف المحمول)؛ يبدأ هو دائماً عملية الاتصال بطلب صفحة أو بيانات أو تنفيذ عملية.

2. الخادم (Server):

الجانب الذي يستقبل الطلبات من العملاء عبر الشبكة، ويعالجها وفق قواعد التطبيق وقاعدة البيانات، ثم يعيد استجابة جاهزة تتضمن النتيجة أو المحتوى المطلوب.

المحور الثاني

البروتوكول الناقل: الفرق بين HTTP و HTTPS الآمن

كتاب الوزارة ص 58 و 59
غير آمن (غير مشفر)

1. بروتوكول HTTP (HyperText Transfer Protocol)

بروتوكول نقل النص التشعبي المستخدم لتبادل الرسائل والصفحات بين العميل والخادم. عيبه القاتل: تنتقل البيانات فيه كنص واضح (Plaintext) غير مشفر، مما يتيح لأي متجسس على الشبكة قراءة كلمات المرور والبيانات الحساسة أو تعديلها أثناء النقل!

آمن ومشفر بالكامل

2. بروتوكول HTTPS (HTTP Secure)

استخدام بروتوكول HTTP عبر اتصال TLS (Transport Layer Security) آمن ومؤمَّن. يضمن: (1) سرية الاتصال (تشفير المحتوى)، (2) سلامة البيانات (اكتشاف أي تلاعب أو تعديل)، و (3) مصادقة الخادم للتأكد من هوية الموقع الحقيقي.

توقف وفكر (ص 59): لماذا يجب أن تستخدم صفحة تسجيل الدخول HTTPS بدلاً من HTTP العادي؟

لأن صفحة تسجيل الدخول تستقبل بيانات اعتماد حساسة وسرية (اسم المستخدم وكلمة المرور)؛ فإذا استُخدم HTTP العادي، ستسافر كلمة المرور مكشوفة ويستطيع أي متجسس على شبكة Wi-Fi أو مسار الإنترنت قراءتها وسرقة الحساب فوراً. بينما يشفر اتصال HTTPS المدعوم بـ TLS كلمة المرور ويمنع قراءتها أو التلاعب بها.

المحور الثالث

أساليب طلب HTTP: المقارنة المعيارية بين GET و POST

كتاب الوزارة ص 59
طريقة GET
طلب مورد أو بيانات من الخادم

تُستخدم عادةً عندما يريد العميل استرجاع أو قراءة بيانات دون إحداث تغيير دائم على الخادم (مثل: عرض صفحة ويب، تصفح مقال، أو استرجاع نتائج البحث عن منتج). تظهر معايير البحث غالباً في شريط العنوان (URL).

طريقة POST
إرسال بيانات ليعالجها الخادم

تُستخدم عادةً عندما يرسل العميل بيانات جديدة أو حساسة ليعالجها الخادم أو يحفظها في قاعدة البيانات (مثل: إرسال اسم المستخدم وكلمة المرور في تسجيل الدخول، إرسال تفاصيل بطاقة الدفع، أو إرسال محتويات نموذج تواصل). ترسل البيانات داخل جسم الطلب (Request Body) وليس في الرابط.

محاكي إرسال طلبات الويب (جرب الأسلوبين واكتشف مسار البيانات): الأسلوب المختار: GET
طبيعة الطلب: GET /search?item=shoes
استرجاع بيانات

يرسل المتصفح طلباً لقراءة قائمة المنتجات. البيانات تطلب مورداً ولا تحدث تعديلاً في قاعدة البيانات، وتظهر المعاملات في رابط العنوان.

المحور الرابع

رموز حالة HTTP (HTTP Status Codes): لغة تقارير الخادم

كتاب الوزارة ص 59

تتضمن الاستجابات المرسلة من الخادم إلى العميل رقماً مكوناً من ثلاثة أرقام يشير إلى نتيجة المعالجة. يسمى هذا الرقم رمز حالة HTTP، ويساعد المتصفح والمستخدم على معرفة ما إذا كان الطلب قد نجح أو أين وقع الخطأ بالتحديد.

200 OK
نجاح (Success)

تمت معالجة الطلب بنجاح تام، وأعاد الخادم الصفحة أو البيانات المطلوبة إلى المتصفح لعرضها.

404 Not Found
المورد غير موجود

المورد أو الصفحة المطلوبة غير موجودة بهذا العنوان (خطأ في جانب العميل ككتابة رابط خاطئ أو صفحة محذوفة).

500 Server Error
خطأ داخلي في الخادم

حدثت مشكلة أو عطل داخلي في جانب الخادم منعه من إكمال الطلب (ولا يحدد الرمز وحده السبب التفصيلي للعطل).

توقف وفكر (ص 60): إذا استقبل المتصفح رمز حالة 404 HTTP، ماذا يجب أن يخبر المستخدم - وأي جانب كانت به المشكلة؟

ماذا يخبر المستخدم: يخبره بأن الصفحة أو الرابط المطلوب غير موجود (مثل: "عذراً، الصفحة غير موجودة").
أي جانب كانت به المشكلة: المشكلة تكون في جانب العميل (Client side) لأنه طلب عنواناً أو مورداً غير متاح أو كتب الرابط خطأ، بخلاف رموز فئة الـ 500 التي تقع فيها المشكلة في جانب الخادم (Server side).

المحور الخامس

واجهة برمجة التطبيقات (API) وصيغة تبادل البيانات (JSON)

كتاب الوزارة ص 59 و 61
API
واجهة برمجة التطبيقات (Application Programming Interface)

مجموعة قواعد واضحة ومحددة تسمح لبرنامج أو تطبيق بطلب بيانات أو وظائف من برنامج أو خدمة أخرى (مثل قيام تطبيق مدرسة بطلب بيانات الطقس من موقع الأرصاد). تعمل كوسيط وعقد رقمي بين الأنظمة المختلفة.

JSON
صيغة كائنات جافاسكريبت (JavaScript Object Notation)

صيغة نصية شائعة وخفيفة لتمثيل وتبادل البيانات المهيكلة بين العميل والخادم؛ تتميز بأنها سهلة القراءة للبشر وسهلة التحليل للحواسيب، وتعتمد على أزواج من المفاتيح والقيم (Key-Value Pairs) والمصفوفات وتدعمها لغات برمجية كثيرة.

تدريب تطبيقي: اقرأ بيانات JSON (كتاب الوزارة ص 61) Key : Value 
{
  "city": "Cairo",
  "temperature": 31
}
التحليل المنهجي المعتمد: يتكون كائن JSON أعلاه من مفتاحين وقيمتين؛ المفتاح الأول هو "city" وقيمته النصية المقابلة هي "Cairo"، والمفتاح الثاني هو "temperature" وقيمته العددية المقابلة هي 31.

خلاصة ليلة الامتحان

تذكر دائماً (أهم مفاتيح الدرس 3-2)

1. دورة الطلب والاستجابة ورموز الحالة:

يبدأ العميل (المتصفح) بإرسال طلب HTTP بأسلوب GET (لجلب بيانات) أو POST (لإرسال بيانات). يعالج الخادم الطلب ويعيد استجابة برمز حالة: 200 (تم بنجاح)، 404 (المورد غير موجود)، أو 500 (خطأ في الخادم).

2. أمان HTTPS وتبادل البيانات بـ JSON:

اتصال HTTPS يشفر البيانات بـ TLS لحمايتها من المتنصتين. وتتيح واجهات API للبرامج تبادل البيانات بسهولة، بصيغة JSON الخفيفة المعتمدة على أزواج المفاتيح والقيم.

حل أسئلة «توقف وفكر» (ص 59 و 60)

السؤال 1 (ص 59): لماذا يجب أن تستخدم صفحة تسجيل الدخول HTTPS بدلاً من HTTP العادي؟

الإجابة: لأن صفحة تسجيل الدخول ترسل بيانات حساسة وسرية للغاية (اسم المستخدم وكلمة المرور)؛ فإذا استُخدم HTTP العادي ستنتقل البيانات كنص صريح مكشوف يسهل اعتراضه وسرقته بواسطة المتنصتين على الشبكة، بينما يشفر اتصال HTTPS البيانات بـ TLS ويحمي سريتها وسلامتها أثناء النقل.

السؤال 2 (ص 60): إذا استقبل المتصفح رمز حالة 404 HTTP، ماذا يجب أن يخبر المستخدم - وأي جانب كانت به المشكلة؟

الإجابة: يجب أن يخبر المستخدم بأن الصفحة أو المورد المطلوب غير موجود بهذا العنوان (مثل: "عذراً، الصفحة غير موجودة"). والمشكلة تكون في جانب العميل (Client side) لأنه طلب عنوان URL خاطئاً أو صفحة تم نقلها أو حذفها.

حل «المثال المحلول» (ص 60)
1. ضع علامة (✓) أو (✗) مع التفسير:

أ) العميل هو الجانب الذي يطلب البيانات أو المعالجة من الخادم، والخادم هو الجانب الذي يعيد الاستجابة: (✓) صواب.

ب) HTTPS هو استخدام HTTP عبر اتصال محمي بـ TLS: (✓) صواب.

ج) أسلوب GET مخصص لإرسال البيانات إلى الخادم: (✗) خطأ (التصحيح: أسلوب GET مخصص لطلب واسترجاع البيانات من الخادم، بينما POST هو المخصص لإرسال البيانات ليعالجها الخادم).

د) رمز حالة 404 HTTP يشير إلى أن المورد المطلوب غير موجود: (✓) صواب.

2. المطابقة:

• 1. بروتوكول اتصال لتبادل البيانات بين متصفحات الويب والخوادم: HTTP (أ).

• 2. واجهة أو مجموعة قواعد محددة تتيح لبرنامج طلب بيانات أو وظائف من برنامج آخر: API (ب).

• 3. بروتوكول اتصال يضيف تشفيراً إلى HTTP: HTTPS (جـ).

سؤال نمط الامتحان المقالي [6 درجات] (ص 60) سلم توزيع الدرجات المعتمد
نص السؤال: «اشرح خطوة بخطوة ما يحدث عندما يطلب المتصفح صفحة ويب ويستجيب الخادم [6 درجات] (أشر إلى العميل، الطلب، طريقة طلب HTTP، الاستجابة، ورمز حالة HTTP).»
1. إرسال الطلب بواسطة العميل (الخطوة الأولى) [درجتان]: يبدأ العميل (متصفح الويب) بإنشاء طلب اتصال HTTP/HTTPS نحو الخادم، ويحدد فيه المورد المطلوب وطريقة الطلب المناسبة؛ مثل طريقة GET إذا كان يطلب عرض صفحة ويب عادية، ويرسل الطلب عبر الشبكة.
2. معالجة الخادم للطلب (الخطوة الثانية) [درجتان]: يستقبل الخادم (Server) الطلب، ويفحص طريقة الطلب وعنوان المورد، ويطبق قواعد المعالجة والتحقق، ويتصل بقاعدة البيانات إذا لزم الأمر لاسترجاع محتوى الصفحة المطلوبة.
3. إرجاع الاستجابة ورمز الحالة (الخطوة الثالثة) [درجتان]: يعيد الخادم حزمة الاستجابة (Response) إلى العميل متضمنة محتوى الصفحة المطلوب مع رمز حالة HTTP يوضح نتيجة المعالجة (مثل الرمز 200 إذا نجحت المعالجة، أو 404 إذا كانت الصفحة غير موجودة)، فيقوم المتصفح بقراءة الرمز وعرض الصفحة للمستخدم.
حل أسئلة «تدرب 1 و 2» (ص 60 و 61)

1. المصطلح الخاص بالجانب الذي يطلب البيانات أو المعالجة من الخادم: العميل (Client).

2. المصطلح الخاص بالجانب الذي يستقبل الطلبات ويعالجها ويعيد الاستجابات: الخادم (Server).

3. البروتوكول المستخدم للوصول إلى الويب عبر اتصال TLS آمن: HTTPS.

4. المصطلح الخاص بطريقة طلب HTTP لاسترجاع البيانات من الخادم: GET.

5. المصطلح الخاص بنظام وقواعد تبادل البيانات بين برمجيات مختلفة: واجهة برمجة التطبيقات (API).

• التركيبة غير المناسبة بين رمز الحالة والمعنى: (جـ) 500 - تمت معالجة الطلب بنجاح (لأن 500 تشير إلى خطأ داخلي في الخادم Server Error، بينما 200 هي التي تعني النجاح).

• الخيار الذي يصف واجهة برمجة التطبيقات بأفضل شكل: (ب) نظام وقواعد لتبادل البيانات بين برمجيات مختلفة.

حل ورشة «فكر كمهندس» وتمرين «اقرأ البيانات» وسؤال «طبق ما تعلمته» (ص 61)

قرار فكر كمهندس (تطبيق ويب لمدرسة):

اختيار الأساليب: (1) تحميل سجل درجات الطالب: أسلوب GET (استرجاع بيانات)، (2) إرسال نموذج تسجيل الدخول: أسلوب POST (إرسال بيانات سرية ومعالجتها)، (3) طلب الجدول الدراسي من مدرسة أخرى: أسلوب GET عبر واجهة برمجة تطبيقات (API). اختيار البروتوكول: يجب استخدام HTTPS لحماية كلمات المرور والدرجات من التنصت والتلاعب. التوصية: نوصي بـ استخدام HTTPS والأسلوب المناسب لكل إجراء (GET للقراءة و POST للإرسال) لضمان الأمان والخصوصية وكفاءة الأداء.

حل تمرين اقرأ البيانات (JSON):

في كائن JSON المعطى: المفتاح الأول هو "city" وقيمته المقابلة "Cairo"، والمفتاح الثاني هو "temperature" وقيمته المقابلة 31.

حل سؤال طبق ما تعلمته (خدمة الطقس عبر API):

طريقة الطلب: أسلوب GET لاسترجاع توقعات اليوم. سبب استخدام HTTPS: لضمان سرية الاتصال ومصادقة خادم الأرصاد ومنع التلاعب ببيانات الطقس أثناء النقل. ميزة استقبال البيانات بصيغة JSON: صيغة نصية خفيفة وسهلة القراءة والتحليل البرمجي وتدعمها لغات البرمجة بكفاءة عالية.

حل التمارين الختامية (ص 62)

إكمال الفراغات: يعتمد اتصال الويب على (1: العميل) الذي يرسل طلباً، و (2: الخادم) الذي يعيد استجابة، ويستخدم بروتوكول (3: HTTP)، ويسمى استخدامه عبر اتصال TLS آمن (4: HTTPS).

تحديد أسلوب الطلب: عرض صفحة ويب (GET) • إرسال معرف وكلمة مرور (POST) • عرض نتائج البحث (GET) • إرسال محتويات نموذج التواصل (POST).

الوصف الأنسب لـ HTTPS: (جـ) بروتوكول يستخدم HTTP عبر اتصال محمي بـ TLS.

فكر وتحدَّ نفسك: رمز الحالة الذي يساعد أكثر على الفهم هو 404 (لمعرفة أن الرابط مفقود وخطأ في العنوان) أو 500 (لمعرفة أن العطل في خادم الموقع نفسه).
